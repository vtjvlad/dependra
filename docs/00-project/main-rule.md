# Главное правило

## Цель

Зафиксировать порядок развития проекта: архитектура раньше полного функционала.

## Правила

1. **Не реализовывать сразу весь функционал.**
2. Сначала — качественная архитектура, независимые интерфейсы, система модулей, расширяемая платформа.
3. Каждая новая возможность подключается как **отдельный модуль** без изменения ядра.
4. Не создавать код «на будущее», который нигде не используется (см. [minimal-implementation.md](../40-development/minimal-implementation.md)).
5. Баланс: простота текущей реализации ↔ возможность расширения.

## Границы

Правило ограничивает процесс разработки и scope PR. Не заменяет продуктовую спеку фич.

## Acceptance criteria

- [ ] Новый функционал не ломает границы модулей ядра
- [ ] Нет пустых абстракций «на потом»
- [ ] Отложенные фичи помечены `deferred`, а не частично зашиты в ядро
