# Модули и ответственность

## Цель

Определить роли модулей так, чтобы каждый можно было разрабатывать, тестировать и сопровождать независимо.

## Модули (целевые)

| Модуль | Ответственность |
|--------|-----------------|
| `cli` | Разбор argv, флаги, коды выхода, запуск pipeline, печать отчёта |
| `core` | Оркестрация анализа, контекст запуска, регистрация инспекторов |
| `scanner` | Обход FS / разрешение путей в рамках задачи |
| `inspectors` | Независимые инспекторы (basic, imports, exports, graph, …) |
| `analyzers` | Общая логика анализа поверх модели (если не в инспекторе) |
| `parsers` | Построение AST / адаптер к внешнему парсеру |
| `dependency` | Построение и запрос зависимостей |
| `graph` | Структуры графа и режимы отображения путей |
| `metadata` | Метаданные файла/проекта (часть — deferred) |
| `permissions` | Права доступа (deferred для MVP UI) |
| `runtime` | Runtime-зависимости запуска (deferred) |
| `plugins` | Точки расширения (deferred) |
| `reporters` | Форматирование text / JSON |
| `cache` | Кэш результатов (минимально / deferred) |
| `utils` | Чистые утилиты без бизнес-логики |
| `types` | JSDoc typedef / общие формы данных |

## Правила

- Не объединять независимые подсистемы в одном модуле.
- Предпочитать новый модуль, если расширение существующего размывает ответственность.
- Модули взаимодействуют только через публичные контракты.

## MVP-минимум для реализации

Для `0.0.1` достаточно реально задействовать: `cli`, `core`, `inspectors`, `parsers`, `dependency`/`graph` (можно совместить тонко на старте **только если** границы контрактов сохранены), `reporters`, `utils`. Остальные каталоги — по мере задач roadmap, не «пустышки ради дерева».

## Acceptance criteria

- [ ] Список ролей согласован с [project-structure.md](project-structure.md)
- [ ] Инспекторы не содержат CLI-парсинг
- [ ] CLI не содержит парсинг AST
