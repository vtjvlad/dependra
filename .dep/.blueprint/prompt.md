 # Проект: Dependra

Ты — опытный архитектор программного обеспечения, Senior Node.js разработчик и инженер по статическому анализу кода.

_______


Общая концепция


Dependra — это универсальная CLI-платформа для исследования файлов, проектов и исходного кода.

Главная цель проекта — предоставить максимально полную информацию о выбранном файле, его окружении, зависимостях, связях с другими файлами, особенностях запуска и качестве исходного кода.
Проект должен изначально проектироваться как масштабируемая модульная система, которую можно будет развивать долгие годы без переписывания архитектуры.
⸻


### Основная задача
Dependra исследует файл и предоставляет максимально полную информацию о нем. Работа строится по принципу независимых инспекторов.
Каждый инспектор анализирует только свою область ответственности.

⸻
### Главное правило

Не реализовывать сразу весь функционал.
Сначала создать качественную архитектуру, независимые интерфейсы, систему модулей и расширяемую платформу.
Каждая новая возможность должна подключаться как отдельный модуль без изменения ядра системы.

⸻

 # Функционал(то что видит пользователь)

Dependra или fds(File Dependency Scoper) это утилита для получения и отображения Общей расширенной углубленной и глубокой информации о файле, но прежде всего Основа это анализ и удобное отображение зависимостей файла

Реализация должна выглядеть как набор функций или операций

Все операции должны быть максимально независимыми и комбинируемыми.

Любая операция должна иметь возможность выполняться:

* отдельно;
* совместно с другими операциями;
* как часть заранее определенного набора действий

функции будут иметь статус приоритета  разработки доработки и разбиваться на уровни (от поверхностного до глубокого анализа )
также функциям (для удобства определения приоритета разработки и внедрения) будет присвоены теги или флаги:

—————

-B             =>            -base                  —                      базовая
-M            =>            -main                  —                      основная
-U             =>           -unfolded             —                     расширенная
-P             =>           -pro                       —                      продвинутая
-D             =>           -deep                    —                      глубокая
-F              =>          -full                         —                     полная
-I               =>          -Intelegence          —                     с использованием ИИ

данные теги ни как не относятся к флагами запуска и примирения утилиты(это исключительно внутренне распределение)
но возможно частично они по взаимсвуются и для cli управления

   ## Набор функций по усовершенствованию файлов (-Е)(-I)(-F)

Помимо анализа, Dependra должна предусматривать возможность выполнения различных операций по автоматической модификации файлов и проекта.

Данный функционал является отдельной подсистемой и не относится к процессу анализа.

Все операции должны быть максимально независимыми и комбинируемыми.

Любая операция должна иметь возможность выполняться:

* отдельно;
* совместно с другими операциями;
* как часть заранее определенного набора действий.

⸻

Основной принцип

По умолчанию Dependra никогда не изменяет файлы.

Результатом анализа являются только отчеты и рекомендации.

Любая модификация файлов должна выполняться только после явного запроса пользователя.

Архитектура должна предусматривать возможность предварительного просмотра изменений (Preview/Dry Run) до их применения.

⸻

Другие операции

Архитектура должна позволять легко добавлять новые операции без изменения существующей системы.

⸻

Комбинирование операций

Любые операции должны иметь возможность выполняться:

* по отдельности;
* последовательно;
* одновременно;
* над одним файлом;
* над несколькими файлами;
* над всем проектом.

Система должна позволять объединять несколько операций в одну команду.

⸻

Независимость операций

Каждая операция должна являться самостоятельным модулем.

Она должна иметь собственный интерфейс и не зависеть от реализации других операций.

Это позволит:

* легко добавлять новые возможности;
* отключать ненужные операции;
* заменять реализацию;
* подключать операции через систему плагинов.

⸻

Использование результатов анализа

Все операции модификации должны использовать результаты предварительного анализа проекта.

Повторное чтение файлов или повторный анализ не допускаются без объективной необходимости.

Результаты анализа должны переиспользоваться всеми последующими этапами обработки.

⸻

Единая модель проекта

Все операции анализа и модификации должны выполняться на основе единого внутреннего представления проекта.

Запрещается выполнять изменения посредством прямой обработки текста файлов, если для данного типа файлов существует более надежное представление.

В качестве внутреннего представления могут использоваться:

* AST (Abstract Syntax Tree);
* граф зависимостей;
* индекс символов;
* модель проекта;
* семантическая модель;
* информация, полученная от Tree-sitter;
* информация, полученная через Language Server Protocol (LSP);
* другие специализированные представления.

Архитектура должна предусматривать возможность одновременного использования нескольких источников анализа.

Например:

AST + Tree-sitter + LSP + собственный анализатор.

Каждый источник должен дополнять общую модель проекта, а не существовать отдельно.

Все последующие операции должны использовать именно эту модель.

Повторный анализ файлов допускается только при объективной необходимости.

⸻

Использование результатов анализа

После построения внутренней модели проекта все операции должны использовать уже полученные данные.

Не допускается повторное чтение файлов или повторное построение AST без необходимости.

Единая модель должна использоваться всеми подсистемами проекта:

* анализаторами;
* модификаторами;
* построителями графов;
* средствами визуализации;
* системой поиска;
* системой рефакторинга;
* системой формирования отчетов.

⸻

Приоритет безопасности

Любая операция, изменяющая содержимое файлов, должна быть максимально безопасной.

Архитектура должна предусматривать возможность:

* предварительного просмотра изменений;
* выборочного применения изменений;
* резервного копирования;
* отмены выполненных операций;
* формирования отчета обо всех внесенных изменениях.

Безопасность и предсказуемость изменений всегда имеют более высокий приоритет, чем степень автоматизации.

⸻



Использование искусственного интеллекта

Архитектура проекта должна предусматривать возможность использования моделей искусственного интеллекта для реализации отдельных функций.

Использование ИИ рассматривается исключительно как дополнительный инструмент и не должно являться обязательным условием работы Dependra.

Все основные функции проекта должны иметь возможность работать без использования AI.

ИИ может применяться, например, для:

* анализа логических ошибок;
* поиска потенциальных проблем в архитектуре;
* прогнозирования возможных ошибок после внесения изменений;
* генерации и улучшения комментариев;
* перевода комментариев;
* объяснения результатов анализа;
* генерации рекомендаций по рефакторингу;
* оценки качества кода;
* интеллектуального поиска зависимостей;
* классификации найденных проблем;
* других задач, где применение ИИ действительно повышает качество результата.

Архитектура должна позволять подключение различных AI-провайдеров или локальных моделей без изменения основной логики приложения.

Отсутствие ИИ не должно ограничивать работу основных возможностей проекта.

 # Архитектура



 ## Общие положения
Этот раздел задает общую архитектурную модель проекта и определяет базовые ориентиры для проектирования, реализации и развития системы.
 
⸻
 
Проект должен строиться на основе модульной архитектуры.
Архитектура системы должна обеспечивать:
* высокую масштабируемость;
* расширяемость;
* независимость компонентов;
* простоту сопровождения на протяжении всего жизненного цикла проекта.
 
⸻
 
Структура проекта должна отражать архитектурную модель системы, а не удобство реализации отдельных компонентов.
Проект не должен развиваться в сторону монолитной архитектуры.
 
⸻
 
 ## Принципы архитектуры
Этот раздел описывает фундаментальные принципы, на которых должна строиться система. Принципы задают направление проектирования и применяются ко всем компонентам проекта без исключения.
 
⸻
 
 ###  Модульность и ответственность
Проект должен состоять из независимых модулей.
Каждый модуль представляет собой самостоятельный логический компонент системы и отвечает только за одну область ответственности.
Каждый модуль должен иметь:
* четко определенное назначение;
* ограниченную область ответственности;
* публичный интерфейс взаимодействия;
* определенные входные данные;
* определенные выходные данные;
* явно описанные зависимости;
* документированные ограничения использования.
 
⸻
 
Каждый модуль должен быть пригоден для:
* независимой разработки;
* независимого тестирования;
* независимого документирования;
* независимого сопровождения.
 
⸻
 
 ###  Контрактность
Взаимодействие между компонентами должно определяться формально описанными контрактами.
Контракт модуля — это совокупность правил, описывающих допустимое взаимодействие с модулем и гарантирующих предсказуемость его поведения для внешних потребителей.
Контракт модуля должен включать:
* публичный API;
* схему входных данных;
* схему выходных данных;
* модель ошибок;
* правила версионирования интерфейса;
* ограничения и гарантии использования;
* условия совместимости.
 
⸻
 
Контракт модуля является единственным допустимым способом описания взаимодействия между модулем и его потребителями.
Внутренняя реализация модуля не является частью контракта и не должна использоваться внешними компонентами.
 
⸻
 
 ###  Изоляция реализации
Внутренняя реализация каждого модуля должна быть скрыта от остальных компонентов системы.
Другие части проекта не должны зависеть от:
* внутреннего устройства модуля;
* деталей его реализации;
* скрытых внутренних соглашений.
 
⸻
 
Изоляция должна обеспечивать возможность замены внутренней реализации без нарушения работы внешних потребителей при сохранении контракта модуля.
 
⸻
 
 ###  Слабая связанность
Связанность между компонентами должна быть минимальной.
Каждый модуль должен знать только о тех компонентах, которые необходимы ему для выполнения своих задач.
Архитектура должна стремиться к:
* слабой связанности;
* явному описанию зависимостей.
 
⸻
 
Не допускается создание сложных цепочек зависимостей между подсистемами.
 
⸻
 
 ###  Масштабируемость
Архитектура должна предусматривать возможность неограниченного расширения функциональности проекта.
Добавление новых возможностей не должно требовать изменения существующих независимых модулей.
Архитектура должна позволять без существенных изменений интегрировать:
* новые анализаторы;
* новые инспекторы;
* новые парсеры;
* новые команды;
* новые отчеты;
* новые плагины;
* новые источники данных;
* новые способы визуализации;
* новые подсистемы.
 
⸻
 
 ###  Расширяемость
Каждая подсистема должна проектироваться с учетом последующего развития.
Новая функциональность должна преимущественно реализовываться путем:
* добавления новых компонентов;
* а не изменения существующих компонентов.
 
⸻
 
При проектировании предпочтение должно отдаваться композиции компонентов вместо модификации уже реализованной логики.
 
⸻
 
 ###  Композиция операций
Любая операция системы должна представлять собой самостоятельную единицу выполнения.
Каждая операция должна иметь возможность выполняться:
* отдельно;
* совместно с другими операциями;
* как часть заранее определенного набора действий;
* как часть автоматического конвейера обработки;
* как часть пользовательского сценария;
* повторно без изменения собственной логики.
 
⸻
 
Операции не должны содержать скрытых предположений относительно порядка своего вызова, если такой порядок явно не определен архитектурой.
Результат выполнения операции должен зависеть исключительно от:
* входных данных;
* конфигурации;
* явно переданного контекста выполнения.
 
⸻
 
 ###  Повторное использование
Любая архитектурная единица должна проектироваться с возможностью повторного использования.
При реализации новой функциональности запрещается дублирование существующей логики, если аналогичная возможность уже реализована в другом компоненте.
 
⸻
 
Общие механизмы должны выделяться в самостоятельные модули или сервисы.
 
⸻
 
 ## Требования к архитектуре
Этот раздел фиксирует обязательные требования к устройству системы. Все требования являются нормативными и должны соблюдаться при проектировании, реализации и изменении архитектуры.
 
⸻
 
 ###  Модули и ответственность
Проект должен состоять из независимых модулей.
Не допускается объединение нескольких независимых подсистем в рамках одного модуля.
Каждый модуль должен быть пригоден для:
* независимой разработки;
* независимого тестирования;
* независимого документирования;
* независимого сопровождения.
 
⸻
 
При реализации новой функциональности предпочтение следует отдавать созданию нового модуля, если расширение существующего нарушает его область ответственности.
 
⸻
 
 ###  Контракт модуля
Каждый модуль должен иметь формально определенный контракт.
Контракт модуля должен включать:
* публичный API;
* схему входных данных;
* схему выходных данных;
* модель ошибок;
* правила версионирования интерфейса;
* ограничения и гарантии использования;
* условия совместимости.
 
⸻
 
Внутренняя реализация модуля не должна использоваться внешними компонентами.
 
⸻
 
 ###  Публичный API
Публичный API модуля — это явно определенный набор функций, методов, команд, событий, сообщений или других точек взаимодействия, через которые внешний код может использовать возможности модуля.
Публичный API должен быть:
* минимально достаточным для выполнения задач модуля;
* свободным от раскрытия внутренних деталей реализации;
* документированным;
* стабильным в пределах объявленной версии интерфейса.
 
⸻
 
 ###  Схема входных данных
Схема входных данных определяет допустимую структуру, типы, обязательность, ограничения и формат данных, принимаемых модулем.
Схема входных данных должна быть:
* формально описана;
* однозначно интерпретируема.
 
⸻
 
Модуль обязан проверять входные данные на соответствие схеме до начала выполнения основной логики.
Недопустимые или неполные входные данные должны приводить к предсказуемой ошибке валидации.
 
⸻
 
 ###  Схема выходных данных
Схема выходных данных определяет структуру, типы, обязательные поля и формат результата, возвращаемого модулем.
Выходные данные должны быть:
* стабильными;
* документированными;
* пригодными для автоматической обработки другими модулями.
 
⸻
 
Модуль не должен возвращать данные, не описанные в контракте, если иное явно не предусмотрено версией интерфейса.
 
⸻
 
 ###  Модель ошибок
Каждый модуль должен иметь формально определенную модель ошибок.
Модель ошибок должна описывать:
* типы возможных ошибок;
* условия их возникновения;
* формат представления ошибки;
* признак повторяемости или неповторяемости ошибки;
* поведение модуля при ошибке;
* границы распространения ошибки.
 
⸻
 
Ошибки должны быть классифицированы как минимум по следующим категориям:
* ошибка валидации входных данных;
* ошибка выполнения;
* ошибка внешней зависимости;
* ошибка конфигурации;
* ошибка несовместимости интерфейса;
* внутренняя критическая ошибка.
 
⸻
 
Ошибки, пересекающие границу модуля, должны быть представлены в документированном и предсказуемом виде.
Модуль не должен скрытно подавлять ошибки, если это приводит к потере управляемости или нарушению контракта.
 
⸻
 
 ###  Версионирование интерфейса
Каждый публичный интерфейс модуля должен иметь версию.
Версия интерфейса должна позволять однозначно определить совместимость между потребителем и поставщиком модуля.
Версионирование должно быть:
* явным;
* документированным.
 
⸻
 
При изменении контракта модуля должны соблюдаться следующие правила:
* изменения, не нарушающие совместимость, допускаются в рамках текущей минорной версии;
* изменения, нарушающие совместимость, требуют увеличения мажорной версии;
* устаревшие интерфейсы должны сопровождаться политикой deprecation;
* удаление устаревшего интерфейса допускается только после завершения периода поддержки.
 
⸻
 
Потребитель модуля должен иметь возможность определить, совместим ли используемый интерфейс с ожидаемой версией.
 
⸻
 
 ###  Границы взаимодействия
Взаимодействие между модулями допускается только через публичные интерфейсы.
Не допускается:
* использование внутренних структур других модулей;
* обращение к их приватной логике;
* опора на скрытые зависимости.
 
⸻
 
Изменение внутренней реализации модуля не должно требовать изменений в других частях системы при сохранении его публичного интерфейса.
Модули не должны содержать неявных предположений о порядке вызова, если такой порядок не определен архитектурой.

 ## Ограничения
Этот раздел перечисляет запреты и недопустимые практики. Ограничения задают границы допустимого архитектурного решения и предотвращают появление решений, нарушающих целостность системы.

* дублировать функциональность между независимыми компонентами;

Любое архитектурное решение должно соответствовать общей архитектурной модели проекта и принципам модульного проектирования.

⸻
 
При реализации новой функциональности следует отдавать предпочтение созданию нового модуля, если расширение существующего компонента приводит к размыванию его ответственности.
 
⸻
 
При проектировании новых возможностей следует выбирать композицию компонентов вместо модификации уже реализованной логики.

Общие механизмы рекомендуется выделять в самостоятельные модули или сервисы, чтобы избежать дублирования и упростить повторное использование.

⸻

⸻
 
При проектировании операций рекомендуется обеспечивать их независимость, повторяемость и возможность включения в разные сценарии выполнения без изменения внутренней логики.

 # Журнал архитектурных решений (ADR — Architecture Decision Records)

Журнал архитектурных решений (ADR — Architecture Decision Records)

Для проекта необходимо вести журнал архитектурных решений.

Его задача — фиксировать все важные технические и архитектурные решения, принятые в ходе разработки проекта.

Данный журнал является официальным источником информации о причинах принятия тех или иных решений.

Он позволяет:

* не возвращаться повторно к уже принятым вопросам;
* понимать причины выбора конкретной реализации;
* сохранять целостность архитектуры проекта;
* упростить дальнейшую разработку;
* сократить необходимость повторного анализа предыдущих обсуждений.

⸻

Когда создавать новую запись

Новая запись создается только при принятии важных решений.

Например:

* изменение архитектуры;
* изменение структуры проекта;
* выбор технологии;
* отказ от определенного решения;
* изменение принципов взаимодействия модулей;
* выбор алгоритма;
* изменение внутреннего формата данных;
* изменение принципов работы CLI;
* изменение системы плагинов;
* изменение формата документации;
* любое решение, которое в будущем может вызвать вопросы “почему было сделано именно так”.

⸻

Когда НЕ создавать запись

Не создавать ADR для:

* исправления мелких ошибок;
* небольших рефакторингов;
* изменения комментариев;
* изменения оформления кода;
* изменения названий локальных переменных;
* мелких оптимизаций.

⸻

Структура записи

Каждая запись должна иметь уникальный номер.

Например:

ADR-0001

ADR-0002

ADR-0003

…

Каждая запись должна содержать следующие разделы.

⸻

Заголовок

Краткое название решения.

Финальная запись создается только после согласования.

ADR — это журнал истории архитектуры проекта.

“Почему было принято именно такое решение?”

Каждое значимое архитектурное решение должно быть зафиксировано один раз и никогда не обсуждаться повторно без появления новых обстоятельств.

Публичная документация также считается неприкосновенной.

Автоматическое изменение запрещено.

Любые изменения сначала оформляются в копиях.

 # Конфиг(файл)

Система пользовательской конфигурации и профилей

В дальнейшем Dependra должна поддерживать систему пользовательской конфигурации, построенную по принципу расширяемости.

Конфигурация должна позволять изменять поведение утилиты без изменения исходного кода.

Архитектура должна изначально предусматривать возможность подключения такой системы.

На ранних этапах реализации наличие данной функциональности не является обязательным.

⸻

Конфигурационный файл

Основным способом настройки должен стать конфигурационный файл проекта.

Формат файла будет определен позднее.

Конфигурационный файл предназначен для хранения пользовательских настроек, профилей и правил работы утилиты.

⸻

Модель конфигурации

Конфигурационная система должна опираться на формальную иерархическую модель.

Структура модели

Конфигурация должна представлять собой дерево параметров, состоящее из следующих уровней:

* глобальные настройки;
* настройки проекта;
* локальные настройки пользователя;
* профили конфигурации;
* параметры командной строки.

Каждый уровень может содержать:

* секции;
* вложенные секции;
* именованные параметры;
* списки значений;
* наборы правил переопределения.

Типы параметров

Конфигурация должна поддерживать следующие типы параметров:

* логические значения;
* целые числа;
* числа с плавающей точкой;
* строки;
* перечисления;
* списки;
* словари или объекты;
* пути к файлам и каталогам;
* команды или сценарии выполнения;
* значения по умолчанию и необязательные параметры.

При необходимости модель должна допускать расширение набора типов без нарушения совместимости.

Правила наследования

Настройки должны наследоваться от более общих уровней к более специфичным.

Базовый порядок наследования должен быть следующим:

1. значения по умолчанию;
2. глобальная конфигурация;
3. конфигурация проекта;
4. локальная конфигурация пользователя;
5. профиль конфигурации;
6. параметры командной строки.

Более высокий уровень должен переопределять значения более низкого уровня.

Если параметр не задан на текущем уровне, он должен наследоваться из ближайшего доступного родительского уровня.

Правила приоритета

При конфликте значений должен применяться следующий приоритет:

* явный параметр командной строки имеет наивысший приоритет;
* затем применяется активный профиль;
* затем локальные пользовательские настройки;
* затем настройки проекта;
* затем глобальные настройки;
* затем значения по умолчанию.

Если несколько источников задают один и тот же параметр на одном уровне, должен использоваться последний явно определенный вариант, если иное не задано схемой конфигурации.

Проверка корректности

Конфигурация должна проходить валидацию по схеме.

Проверка должна включать:

* соответствие типов;
* допустимость значений;
* корректность вложенности;
* проверку обязательных параметров;
* проверку совместимости между связанными настройками.

⸻

Возможности конфигурации

Конфигурация должна позволять:

* изменять поведение отдельных подсистем;
* изменять режимы работы;
* определять значения по умолчанию;
* включать или отключать отдельные анализаторы;
* изменять уровень анализа;
* изменять глубину анализа;
* создавать собственные режимы работы;
* сохранять пользовательские настройки.

⸻

Настройка CLI

Конфигурация должна позволять:

* назначать пользовательские флаги;
* переопределять стандартные флаги;
* создавать псевдонимы (алиасы) для команд;
* создавать сокращенные варианты часто используемых команд;
* задавать параметры по умолчанию.

⸻

Пользовательские сценарии

Пользователь должен иметь возможность создавать собственные сценарии выполнения.

Каждый сценарий представляет собой заранее определенную последовательность действий.

Например:

* запуск нескольких анализаторов;
* выполнение нескольких модификаций;
* формирование отчета;
* построение графа;
* сохранение результата.

Архитектура должна позволять создавать любое количество подобных сценариев.

⸻

Комбинирование функций

Конфигурация должна позволять объединять несколько независимых функций в одну пользовательскую операцию.

Например:

* анализ;
* построение графа;
* проверка качества;
* экспорт отчета.

Все перечисленные действия должны иметь возможность запускаться как одна пользовательская команда.

⸻

Настройка вывода

Пользователь должен иметь возможность управлять отображением результатов.

Например:

* объединять результаты различных анализаторов;
* изменять порядок отображения;
* скрывать отдельные разделы;
* группировать результаты;
* изменять степень детализации;
* создавать собственные шаблоны отображения.

⸻

Сохранение результатов

Конфигурация должна предусматривать возможность автоматического сохранения результатов.

Например:

* в файл;
* в каталог;
* в отдельный отчет;
* в несколько файлов одновременно.

Поддержка форматов вывода будет расширяться по мере развития проекта.

⸻

Профили

В дальнейшем должна появиться возможность создавать различные профили конфигурации.

Например:

* быстрый анализ;
* полный анализ;
* анализ качества;
* исследование зависимостей;
* пользовательские профили.

Архитектура должна позволять добавлять новые профили без изменения базовой модели конфигурации.

⸻

Расширяемость

Система конфигурации должна проектироваться независимо от остальных подсистем.

Добавление новых параметров, режимов, профилей и сценариев не должно требовать изменения существующих конфигурационных файлов и не должно нарушать совместимость с уже определенными настройками.

Все новые возможности должны подключаться через расширение схемы, а не через изменение базовой логики.

⸻

Дальнейшее развитие

После завершения разработки CLI аналогичные возможности должны стать доступны через отдельный TUI-интерфейс.

TUI не заменяет CLI, а является дополнительным способом взаимодействия с Dependra.

Основные принципы:

* единая логика работы;
* единая система конфигурации;
* единая внутренняя модель проекта;
* общие анализаторы, модификаторы и механизмы визуализации.

CLI и TUI должны использовать одни и те же внутренние подсистемы.

Различаться должен только пользовательский интерфейс.

Все настройки, профили и пользовательские сценарии должны одинаково работать как в CLI, так и в TUI.

 # TUI/CLI

Дополнительный пользовательский интерфейс (TUI)

Система пользовательской конфигурации должна изначально проектироваться таким образом, чтобы в дальнейшем ее можно было использовать не только через конфигурационные файлы и CLI, но и через полноценный интерактивный пользовательский интерфейс.

Реализация TUI не является частью первоначальной разработки и рассматривается как отдельный этап развития проекта.

⸻

TUI-приложение

Назначение

В дальнейшем на базе ядра Dependra должно быть разработано отдельное консольное приложение с полноценным TUI-интерфейсом.

TUI является дополнительным способом взаимодействия с Dependra.

TUI не является заменой CLI.
Он не заменяет CLI и не изменяет существующую архитектуру проекта.

CLI остается основным способом взаимодействия с утилитой и основным интерфейсом автоматизации.

Основной задачей TUI является повышение удобства использования утилиты без необходимости запоминать большое количество команд, параметров, флагов и структуры конфигурационных файлов.

CLI остается основным интерфейсом автоматизации, написания сценариев и интеграции с другими инструментами.

TUI представляет собой дополнительный пользовательский интерфейс, предназначенный для более удобной работы с результатами анализа, исследования проекта и выполнения операций без необходимости использовать большое количество команд и флагов.

⸻

Архитектурный принцип

Использование общего ядра

TUI не должен содержать собственной реализации анализа, модификации, поиска, конфигурации или других функций.

Вся логика должна использовать единое публичное API ядра Dependra.

Любая функция, доступная через CLI, должна быть доступна и через TUI без повторной реализации.

Различаться должен исключительно пользовательский интерфейс.

Ядро проекта должно быть полностью независимым от пользовательского интерфейса.

Вся бизнес-логика должна находиться исключительно в ядре Dependra.

CLI и TUI являются лишь различными способами взаимодействия с одним и тем же API.

Запрещается реализовывать отдельную логику анализа специально для TUI.

Любая функция, доступная в TUI, должна использовать существующий API ядра проекта.

⸻

Основные возможности TUI

TUI должен предоставлять доступ ко всем возможностям CLI.

При этом пользователь должен иметь возможность выполнять большинство операций без необходимости помнить команды, параметры и большое количество флагов.

Интерфейс должен быть максимально простым, логичным и интуитивно понятным.

⸻

Навигация

TUI должен обеспечивать удобную навигацию по проекту.

Например:

* просмотр дерева каталогов;
* переход между файлами;
* просмотр результатов анализа;
* быстрый поиск;
* фильтрацию;
* сортировку;
* переход между связанными файлами;
* переход по графу зависимостей.

⸻

Просмотр результатов

TUI должен значительно улучшать читаемость выводимой информации.

Должны поддерживаться:

* сворачиваемые разделы;
* группировка данных;
* цветовое оформление;
* отображение зависимостей;
* древовидные структуры;
* таблицы;
* панели;
* карточки;
* различные режимы просмотра.

⸻

Выполнение операций

Через TUI пользователь должен иметь возможность выполнять все доступные операции проекта.

Например:

* запуск анализа;
* запуск модификаций;
* построение графов;
* просмотр зависимостей;
* просмотр статистики;
* запуск пользовательских сценариев;
* управление профилями конфигурации.

⸻

Работа с конфигурацией


TUI должен предоставлять удобный встроенный конфигуратор.

Конфигуратор предназначен для настройки Dependra без необходимости вручную редактировать конфигурационные файлы.

Через него пользователь должен иметь возможность:

* изменять настройки;
* создавать и редактировать профили;
* изменять режимы работы;
* настраивать уровни анализа;
* создавать пользовательские сценарии;
* изменять параметры отображения результатов;
* управлять пользовательскими настройками.

Все изменения должны сохраняться в ту же систему конфигурации, которую использует CLI.

⸻


Работа с результатами

TUI должен обеспечивать удобную работу с результатами анализа.

Например:

* сохранение результатов;
* экспорт в различные форматы;
* повторное открытие сохраненных отчетов;
* сравнение результатов нескольких запусков;
* поиск по результатам;
* фильтрацию данных;
* навигацию по большим отчетам.

Использование TUI не должно требовать дополнительной настройки конфигурационных файлов.

Большинство действий должно выполняться через пользовательский интерфейс.

⸻

* просмотр больших отчетов без необходимости повторного запуска анализа.

⸻

Сохранение результатов

Через TUI пользователь должен иметь возможность сохранять результаты анализа в различные форматы без необходимости предварительной настройки конфигурации или использования большого количества параметров командной строки.


⸻

Концепция интерфейса

При разработке допускается использовать концепцию легковесных консольных приложений с интуитивной навигацией.

В качестве ориентира могут рассматриваться файловые менеджеры и консольные анализаторы наподобие ncdu, однако без копирования их архитектуры, интерфейса или принципов реализации.

Главной целью является создание быстрого, отзывчивого и удобного пользовательского интерфейса, который позволяет эффективно работать даже с большими проектами.

⸻



Возможная концепция интерфейса

В качестве ориентира допускается использование концепции легковесных консольных приложений, подобных файловым менеджерам и системным анализаторам.

Например, по удобству взаимодействия интерфейс может напоминать такие утилиты, как ncdu, однако без копирования их архитектуры или поведения.

Основной принцип — быстрый, отзывчивый и минималистичный интерфейс, позволяющий эффективно работать даже с очень большими проектами.

⸻

Использование API

TUI должен использовать исключительно публичное API Dependra.

Любая возможность, появившаяся в ядре проекта, должна автоматически становиться доступной как для CLI, так и для TUI без дублирования реализации.

Это гарантирует единое поведение всех интерфейсов и упрощает дальнейшее развитие проекта.

 # Глоссарий
проекта Dependr
 

Назначение
Глоссарий является единым словарем терминов проекта Dependra. Его задача — закрепить единое значение используемых понятий и обеспечить одинаковое понимание терминологии во всех документах проекта.
Все документы, исходный код, архитектурные описания, ADR, Roadmap и внутренняя документация должны использовать определения, приведенные в настоящем разделе. Использование разных названий для одной и той же сущности не допускается.
Для удобства навигации связанные понятия дополнительно связаны перекрестными ссылками, в частности между Единой моделью проекта, AST, LSP, Семантической моделью, Символом, Графом зависимостей и Индексом символов.

 ## Основной принцип
      
Все термины, используемые в документации проекта, должны соответствовать определениям, приведенным в настоящем глоссарии.
При появлении нового фундаментального понятия оно должно быть сначала добавлено в глоссарий и только после этого использоваться в других документах проекта.
Глоссарий является единым источником терминологии проекта и служит основой для поддержания согласованности всей документации.
* Связанные понятия должны по возможности ссылаться друг на друга, чтобы облегчать переходы между разделами и поддерживать целостное понимание таких связок, как AST → Семантическая модель → Единая модель проекта → Граф зависимостей → Диагностика и Рефакторинг.



 ## Термины

Адаптер (Adapter)
Компонент, обеспечивающий взаимодействие Dependra с внешними инструментами, библиотеками или сервисами посредством единого внутреннего интерфейса.

Анализ (Analysis)
Процесс получения структурированной информации о проекте без изменения его содержимого. В зависимости от режима работы анализ может быть:
* базовым;
* расширенным;
* глубоким;
* полным;
* специализированным.
Анализ использует AST, LSP, Семантическую модель, Индекс символов и другие источники данных для формирования Единой модели проекта. Результаты анализа применяются в Диагностике, Рефакторинге и построении Графа зависимостей.

Анализатор (Analyzer)
Компонент, выполняющий анализ определенного аспекта проекта и формирующий структурированный результат.

Backend
Совокупность внутренних подсистем Dependra, реализующих анализ, обработку данных и выполнение операций.

Визуализация (Visualization)
Графическое, текстовое или схематическое представление результатов анализа, предназначенное для упрощения восприятия структуры проекта и взаимосвязей между его компонентами.

Граф зависимостей (Dependency Graph)
Ориентированный граф, отображающий связи между сущностями проекта. Вершинами графа являются файлы, модули или символы. Ребра графа описывают существующие зависимости между ними.
Граф используется для анализа архитектуры, поиска циклических зависимостей, оценки влияния изменений и визуализации структуры проекта.
Граф зависимостей строится на основе данных из Единой модели проекта, Семантической модели, AST, LSP и Индекса символов. Он особенно важен для Диагностики и Рефакторинга, поскольку позволяет оценивать последствия изменений.

Граф символов (Symbol Graph)
Граф, отображающий взаимосвязи между символами проекта. Используется для анализа использования сущностей, поиска зависимостей и оценки влияния изменений.

Диагностика (Diagnostics)
Процесс выявления потенциальных ошибок, несоответствий, нарушений архитектуры, проблем зависимостей и других отклонений от ожидаемого состояния проекта.
Диагностика использует результаты анализа, Семантическую модель, Граф зависимостей и Индекс символов. Она помогает обнаруживать циклы, недостижимые символы, некорректные импорты, несоответствия между экспортами и фактическим использованием кода.

Драйвер (Driver)
Компонент, реализующий непосредственное взаимодействие с конкретным внешним инструментом, программой или системой.

Единая модель проекта (Unified Project Model)
внутреннее представление проекта, объединяющее результаты анализа исходного кода, структуры каталогов, зависимостей, символов, связей между сущностями и других доступных источников информации.
Единая модель проекта является основой практически всех операций Dependra. Она не представляет собой копию текста файлов и не зависит от какого-либо одного механизма анализа.
Ее задача — сформировать согласованную, нормализованную и расширяемую модель проекта, пригодную для выполнения анализа, диагностики, поиска зависимостей, рефакторинга, построения графов зависимостей, генерации отчетов и других операций.
Все операции, изменяющие проект, должны опираться именно на Единую модель проекта, а не выполнять изменения непосредственно над текстом файлов.
Единая модель проекта формируется на основе данных, полученных из AST, LSP, Семантической модели и других источников анализа.

Зависимость (Dependency)
Любая связь, при которой одна сущность требует существования другой для корректной работы. В рамках проекта Dependra различаются несколько видов зависимостей:
* файловые;
* модульные;
* пакетные;
* библиотечные;
* системные;
* зависимости среды выполнения;
* зависимости компиляции;
* логические зависимости;
* косвенные зависимости.
Зависимость является одним из ключевых понятий для Графа зависимостей, Единой модели проекта и Диагностики. Связи между Импортом, Экспортом и Модулем также выражают зависимости между сущностями.

Зона анализа (Analysis Scope)
Часть проекта, в пределах которой выполняется анализ. Зоной анализа может быть отдельный файл, каталог, пакет, модуль или весь проект.

Импорт (Import)
Механизм получения доступа к символам, экспортируемым другим модулем. Импорт определяет зависимость текущего модуля от внешней сущности.
Импорт является одним из основных источников информации для Семантической модели и Графа зависимостей. Анализ импортов помогает определить, какие модули и символы используются в проекте и как они связаны между собой.

Индекс проекта (Project Index)
Централизованная структура данных, содержащая сведения обо всех обнаруженных объектах проекта. Используется для быстрого доступа к результатам анализа без необходимости повторного исследования файлов.

Индекс символов (Symbol Index)
Централизованная база сведений обо всех обнаруженных символах проекта и связях между ними. Он используется для быстрого поиска, навигации, анализа связей, зависимостей и выполнения операций рефакторинга.
Индекс символов опирается на данные AST, LSP и Семантической модели. Он служит одним из ключевых источников для построения Графа зависимостей и уточнения Единой модели проекта.

Инспектор (Inspector)
Компонент, реализующий специализированную проверку или диагностику отдельных характеристик проекта.

Исходный файл (Source File)
Файл, являющийся непосредственным объектом анализа, проверки, обработки или модификации.

Источник данных (Provider)
Компонент или внешний инструмент, предоставляющий информацию для анализа. Источником данных могут выступать парсеры, языковые серверы, внешние библиотеки, системные средства и другие механизмы получения информации.

Конвейер операций (Pipeline)
Последовательность взаимосвязанных операций, выполняемых в определенном порядке для достижения общего результата.

Контекст анализа (Analysis Context)
Совокупность данных, доступных операции анализа в момент ее выполнения. Контекст может включать сведения о проекте, конфигурации, окружении, зависимостях и ранее полученных результатах анализа.

Кэш (Cache)
Временное хранилище результатов анализа, предназначенное для сокращения времени повторной обработки проекта.

Модификация (Modification)
Частный случай преобразования, приводящий к непосредственному изменению содержимого файлов проекта.

Модуль (Module)
Самостоятельная логическая единица программы, имеющая собственную область ответственности и взаимодействующая с другими модулями через явно определенные интерфейсы.
В различных языках программирования модулем может являться файл, пакет, библиотека, пространство имен или другая единица организации кода.
Модуль тесно связан с Импортом, Экспортом и Зависимостью, поскольку именно через эти механизмы описываются его внешние связи. Модули часто выступают вершинами Графа зависимостей и важными элементами Единой модели проекта.

Операция (Operation)
Минимальная независимая функциональная единица Dependra. Каждая операция должна иметь возможность выполняться самостоятельно, совместно с другими операциями или в составе заранее определенного сценария.

Отчет (Report)
Документ или структурированный вывод, содержащий результаты анализа, диагностики, проверки либо других операций Dependra.

Парсер (Parser)
Компонент, преобразующий исходный текст в структурированное внутреннее представление, пригодное для дальнейшего анализа.

Плагин (Plugin)
Независимое расширение функциональности Dependra, реализующее дополнительные возможности анализа, обработки, визуализации или модификации проекта и подключаемое без изменения архитектуры основного проекта.
Плагины интегрируются через публичные внутренние интерфейсы и не должны нарушать архитектурную целостность системы.
Плагины могут расширять Анализ, Диагностику, Рефакторинг и способы представления Единой модели проекта. При этом они должны сохранять совместимость с Семантической моделью, Индексом символов и Графом зависимостей.

Преобразование (Transformation)
Любая операция, изменяющая внутреннее представление проекта или его исходные данные в соответствии с заданными правилами.

Проект (Project)
Совокупность файлов, каталогов, зависимостей, конфигурации, ресурсов и других объектов, рассматриваемых Dependra как единое целое и являющихся объектом анализа.

Профиль анализа (Analysis Profile)
Предварительно определенный набор операций, настроек и параметров анализа, предназначенный для решения конкретной задачи.

Рабочая область (Workspace)
Каталог, выбранный пользователем в качестве области работы Dependra. Рабочая область может содержать один или несколько независимых проектов.

Разрешение зависимостей (Dependency Resolution)
Процесс определения, поиска, проверки и построения связей между всеми зависимостями проекта.

Результат анализа (Analysis Result)
Structured представление данных, полученных в результате выполнения одной или нескольких операций анализа.

Рефакторинг (Refactoring)
Изменение структуры проекта без изменения его внешнего поведения.
Все операции рефакторинга должны выполняться на основании Единой модели проекта и гарантировать сохранение корректности исходного кода.
Рефакторинг опирается на Индекс символов, Семантическую модель и Граф зависимостей, чтобы безопасно изменять символы, модули, импорты и экспорты.

Семантическая модель (Semantic Model)
Внутреннее представление смысловых связей проекта. Она описывает не только синтаксическую структуру программы, но и смысл объектов, их роли, зависимости, области видимости, отношения между символами и контекст использования.
Семантическая модель объединяет информацию, полученную из различных источников анализа, включая AST, LSP и другие специализированные инструменты.
Семантическая модель служит промежуточным слоем между исходными данными анализа и Единой модели проекта. Она особенно важна для точного определения связей между модулями, импортами, экспортами и символами.

Символ (Symbol)
Именованная сущность исходного кода. К символам относятся:
* функции;
* методы;
* классы;
* интерфейсы;
* структуры;
* перечисления;
* пространства имен;
* переменные;
* константы;
* параметры;
* свойства;
* типы;
* модули;
* пакеты;
* другие именованные элементы языка программирования.
Символ является базовой единицей для Индекса символов, Семантической модели и Графа зависимостей. Именно через символы описываются многие связи между сущностями проекта, включая ссылки, объявления, определения и области видимости.

Снимок проекта (Project Snapshot)
Зафиксированное состояние проекта в определенный момент времени, используемое для сравнения, анализа изменений или повторного исследования.

Среда выполнения (Runtime)
Программное окружение, необходимое для запуска, выполнения или анализа исследуемого проекта.

Уровень анализа (Analysis Level)
Степень глубины исследования проекта. Уровень анализа определяет объем выполняемых операций, используемые источники информации и детализацию получаемого результата.

Frontend
Средство взаимодействия пользователя с Dependra. К фронтендам относятся CLI, TUI, API и другие пользовательские интерфейсы.

Экспорт (Export)
Механизм предоставления символов другим модулям. Экспорт определяет публичный интерфейс модуля.
Экспорт является обратной стороной Импорта и вместе с ним формирует видимые связи между частями проекта. Экспортируемые символы особенно важны для Индекса символов, Семантической модели и Графа зависимостей.

Языковой адаптер (Language Backend)
Подсистема, реализующая поддержку конкретного языка программирования, включая анализ, диагностику и работу с его особенностями.

AST (Abstract Syntax Tree)
Абстрактное синтаксическое дерево. AST представляет исходный код в виде дерева синтаксических конструкций. Оно описывает структуру программы независимо от ее текстового оформления.
AST является одним из основных источников для построения Семантической модели и Единой модели проекта.
AST используется для:
* анализа структуры исходного кода;
* поиска функций;
* поиска классов;
* поиска переменных;
* поиска импортов и экспортов;
* поиска объявлений;
* навигации по коду;
* безопасного рефакторинга;
* построения внутренней модели проекта.
AST тесно связан с Символами, поскольку именно из синтаксической структуры извлекаются многие именованные сущности.

CST (Concrete Syntax Tree)
Конкретное синтаксическое дерево. В отличие от AST сохраняет практически полную структуру исходного текста, включая многие синтаксические элементы. Используется отдельными парсерами и инструментами анализа.

LSP (Language Server Protocol)
Открытый протокол взаимодействия редакторов и инструментов разработки с языковыми серверами.
LSP предоставляет семантическую информацию о проекте, которая зачастую недоступна при обычном синтаксическом анализе.
Через LSP могут быть получены:
* сведения о символах;
* определения;
* объявления;
* ссылки;
* типы;
* диагностика;
* навигация;
* подсказки;
* информация о переименовании;
* данные для рефакторинга;
* другая информация, предоставляемая конкретным языковым сервером.
Использование LSP является дополнительным источником информации и не является обязательным для работы Dependra.
LSP дополняет AST и помогает уточнять Семантическую модель, Индекс символов и связи, используемые при построении Графа зависимостей.
